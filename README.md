# FasalSetu Backend

> **AI-Powered Agricultural Decision Platform for Indian Farmers**  
> Hackathon MVP — Feature 1: Crop Recommendation | Feature 2: Market Price Comparison | Feature 3: Farmer Q&A Assistant | Feature 3B: Voice Input Q&A | Feature 4: Conversational Follow-ups | Feature 5: Image-based Crop Diagnosis | Feature 7: Price Negotiation | Feature 8: Answer Feedback Loop | Feature 9: Real Authentication | Feature 10: Auth-Wired Marketplace & Browse

---

## 🌾 Overview

**FasalSetu** provides intelligent, data-driven decision support for Indian farmers:
1. **Crop Recommendation Engine**: Analyzes soil nutrients (Nitrogen, Phosphorus, Potassium) and local climate metrics (Temperature, Humidity, Soil pH, Rainfall) before planting to recommend the top crop + alternatives with statistical confidence.
2. **Market Price Comparison Engine**: Enables farmers to compare live/recent commodity prices across nearby agricultural mandis (markets) for any of the 22 supported crops, filter by state (case-insensitively), and identify the market offering the best return.
3. **Farmer Q&A Assistant**: Single-turn regional-language question answering endpoint powered by Groq's high-speed inference (`llama-3.1-8b-instant`). Farmers can ask pest control, sowing timing, fertilizer usage, and general crop care questions in Hindi, English, and regional languages and receive immediate, structured advice in the same language with safety disclaimers.
4. **Voice Input for Farmer Q&A (Feature 3B)**: Enables farmers to submit voice recordings (`.m4a`, `.mp3`, `.wav`, `.webm`) of their questions instead of typing. Transcribed using Groq Whisper (`whisper-large-v3-turbo`) with an explicit 15-second timeout, then answered by the Q&A engine in the farmer's language with safety disclaimers.
5. **Conversational Follow-ups (Feature 4)**: Enables farmers to ask follow-up questions referencing prior dialogue within the same session. By providing an optional `session_id` (UUID generated by frontend), the backend injects up to 3 previous Q&A turns in chronological order into Groq's prompt context, with previous answers truncated at 300 characters for token efficiency. Works seamlessly across both text and voice endpoints, with graceful stateless fallback when `session_id` is omitted or unrecorded.
6. **Image-based Crop Diagnosis (Feature 5)**: Enables farmers to upload a photograph of a diseased or damaged crop/leaf (`.jpg`, `.jpeg`, `.png`, `.webp`, up to 10MB) and receive an instant visual diagnosis, confidence note, actionable treatment steps, and safety disclaimer in their language. Powered by Groq's high-performance vision model (`qwen/qwen3.6-27b`), complete with sliding window rate limiting (10 req/min), dedicated database audit logging (`CropDiagnosisLog`), and graceful fallback (503) if the preview model is decommissioned or temporarily unavailable.
7. **Price Negotiation Engine & Buyer Marketplace (Features 7 & 10)**: Real JWT authenticated agricultural marketplace. Farmers list crops with asking prices, buyers discover open listings (filtered by status and crop), submit offers, and negotiate in auditable threads. Enforces role-based permissions, listing ownership checks, negotiation party authorization (403 for third parties), real foreign key constraints to `users.id`, and personal dashboards (`GET /api/my/offers` for buyers and `GET /api/my/listings` for farmers).
8. **Answer Feedback Loop (Feature 8)**: Enables farmers and reviewers to submit thumbs-up (`"up"`) or thumbs-down (`"down"`) feedback and optional comments (up to 500 characters) on any AI-generated response across Text Q&A, Voice Q&A, and Image Diagnosis. Implements idempotent overwrite behavior for seamless correction of accidental taps, returns the row's `log_id` across all AI response schemas, and persists ratings without extra joins.
9. **Real Authentication for Both Roles (Feature 9)**: Provides phone + password registration and login for both `farmer` and `buyer` roles with bcrypt hashing and JWT bearer tokens (`python-jose`). Supports dual-role accounts on the same phone number via a composite unique constraint `(phone, role)`, enforces anti-enumeration uniform `401 Unauthorized` responses on failed logins, and offers `get_current_user` and `require_role(...)` dependencies for route protection.

## 🚀 Quick Start (Docker Compose)

The entire stack (FastAPI Backend + PostgreSQL Database) launches with a single command.

### 1. Launch Services
```bash
# From project root:
docker-compose up --build
```

- **Backend API**: [http://localhost:8000](http://localhost:8000)
- **Interactive Swagger Docs**: [http://localhost:8000/docs](http://localhost:8000/docs)
- **ReDoc Documentation**: [http://localhost:8000/redoc](http://localhost:8000/redoc)
- **PostgreSQL**: `localhost:5432` (`fasalsetu_db`)

> **Startup Ordering Guarantee**: Docker Compose enforces `condition: service_healthy` on the PostgreSQL container (`fasalsetu-db`). The backend starts only after PostgreSQL is fully initialized and accepting connections.
>
> **Build-Time ML Model Training**: The Random Forest model is trained at **Docker build time** inside the Dockerfile (`RUN python -m app.ml.train_crop_model`), baking `crop_rf_model.joblib` into the container image. Container startup only loads the pre-baked artifact into memory.
>
> **Automatic Database Seeding**: On first startup, the application initializes all database tables (`init_db`) and automatically seeds 20 mandis and commodity prices across 5 states (`seed_market_prices`).

## 🗄️ Database Configuration & SQLite Boundary

- **Production & Hackathon Demo**: The application connects to **PostgreSQL** (`postgresql://postgres:postgres@db:5432/fasalsetu_db`).
- **SQLite Usage Boundary**: SQLite is **strictly isolated to the automated test suite** (`tests/conftest.py`) using in-memory sessions (`sqlite:///:memory:`). Tests NEVER touch or modify the PostgreSQL database.
- **Local Development without Docker**: If running locally on host Python, you can point to local PostgreSQL or set `DATABASE_URL=sqlite:///./fasalsetu_dev.db` in your local `.env`.
- **Groq API Configuration**: Set `GROQ_API_KEY` in `.env` to enable the Farmer Q&A Assistant and Whisper Voice Transcription. Automated tests mock all Groq client calls and do not consume credits or require a live key.

### 6. Conversational Follow-ups (Feature 4)
Allows farmers to ask follow-up questions referencing previous answers in the same dialogue session instead of treating every question statelessly.

#### How It Works:
1. **Frontend-Managed Session Lifecycle**:
   - On the first question in a session, the client can omit `session_id` (or pass a new UUID).
   - The backend auto-generates a UUID `session_id` if omitted and returns it in the response.
   - For all subsequent follow-up questions, the client sends this `session_id` back in the request body (text) or form data (voice).
2. **Context Window & History Cap**:
   - The backend queries the last `N=3` (`MAX_CONVERSATION_HISTORY = 3`) turns from `FarmerQALog` for the provided `session_id`.
   - History turns are ordered **chronologically from oldest to newest** so the conversation flows naturally before the current question.
   - Previous answers are truncated at 300 characters (`MAX_HISTORY_ANSWER_LENGTH = 300`) to preserve tokens for the answer while maintaining context.
3. **Stateless Fallback**:
   - If `session_id` is missing or has no prior logs in the database, the endpoint processes the question statelessly without errors and returns a valid `session_id`.
4. **Voice Endpoint Parity**:
   - `POST /api/farmer-qa/voice` supports the exact same `session_id` form field, enabling voice follow-ups to text queries and vice versa.

##### Turn 1 — Initial Question (Omits `session_id`):

### 7. Price Negotiation & Buyer Marketplace Browse (Features 7 & 10)
Enables an authentic, JWT-secured agricultural marketplace between farmers and buyers. Farmers list crops with asking prices, buyers browse active market listings, submit offers, and engage in multi-round counter-negotiations until an agreement is reached or rejected.

> [!IMPORTANT]
> **Feature 10 Auth Wiring & Security Enforcements**:
> - **Zero Loose Identifiers**: `farmer_id` and `buyer_id` are **completely removed** from request bodies. Identities are derived strictly from authenticated JWT bearer tokens (`current_user.id`).
> - **Farmer Listing Ownership**: Creating a listing requires `role="farmer"`. A farmer cannot create a listing under another person's ID. Countering or acting on a listing requires the farmer to actually own that listing (**403 Forbidden** if not).
> - **Negotiation Party Authorization**: Only the legitimate recipient party is authorized to accept or reject an offer (**403 Forbidden** for third parties or the offer creator).
>   - Buyer offers can only be accepted/rejected by the listing's owning farmer.
>   - Farmer counter-offers can only be accepted/rejected by the specific buyer involved on that negotiation thread.
> - **Buyer Thread Continuity**: A buyer cannot counter into another buyer's private negotiation thread on a listing (**403 Forbidden**).

#### Marketplace Endpoints:
| Method | Path | Auth Required | Role | Description |
| :--- | :--- | :--- | :--- | :--- |
| `POST` | `/api/listings` | **Yes** | `farmer` | Create a new crop listing (`farmer_id` set from token) |
| `GET` | `/api/listings` | Optional | Any | Browse marketplace listings (`status` defaults to `open`) |
| `GET` | `/api/listings/{id}` | Optional | Any | View listing details with complete chronological negotiation thread |
| `POST` | `/api/listings/{id}/offers` | **Yes** | `buyer` / `farmer` | Submit initial offer (buyer) or counter-offer (buyer or owning farmer) |

| `GET` | `/api/my/listings` | **Yes** | `farmer` | Returns all listings owned by authenticated farmer with full offer threads |

#### Database Foreign Key Constraints & Migration Notice:
- `CropListing.farmer_id` and `CropOffer.buyer_id` are configured as proper `Integer, ForeignKey("users.id", ondelete="CASCADE")`.
- **One-Time Migration Cleanup Notice**: Any legacy database rows created under early unauthenticated schemas with string IDs (e.g. `"farmer_01"`) will not map to integer user IDs. In local environments, legacy rows in `fasalsetu_dev.db` must be cleared or migrated before running.

#### Marketplace Browse & Location Gap Flag:
- `GET /api/listings` defaults to `status="open"` (excluding `sold` and `withdrawn` listings by default). Pass `status=all` to see listings across all states.
- **Flagged Gap**: Farmer location (state/district) is not currently captured in the `User` profile model (`users` table captures phone, role, password, and name only). Geographic filtering is deliberately deferred until user profile location fields are formally added.

#### State Machine & Validation Rules:
1. **Listing Status**:
   - `open`: Initial state on creation.
   - `negotiating`: Automatically set when an initial buyer offer is submitted.
   - `sold`: Deal closed when either party accepts a pending offer.
   - `withdrawn`: Terminal state if listing is cancelled.
2. **Offer Status**:
   - `pending`: Active offer awaiting response.
   - `countered`: Marked when superseded by a new counter-offer referencing `parent_offer_id`.
   - `accepted`: Deal closed; triggers listing status $\rightarrow$ `sold`.
   - `rejected`: Offer declined; listing status reverts to `open`.
3. **Safety Guardrails & Status Codes**:
   - **401 Unauthorized**: Missing or invalid JWT Bearer token on protected routes.
   - **403 Forbidden**: Role mismatch (e.g. buyer attempting to create a listing), unowned listing action, or third party attempting to accept/reject.
   - **409 Conflict**: Submitting an offer on a `sold` or `withdrawn` listing.
   - **422 Unprocessable Content**: Acting on a stale/countered offer, or non-positive offer amount.

### 8. Answer Feedback Loop (Feature 8)
Enables farmers and app reviewers to submit thumbs-up (`"up"`) or thumbs-down (`"down"`) feedback and optional comments (up to 500 characters) on any logged AI response from Farmer Q&A (Feature 3/3B) and Image Crop Diagnosis (Feature 5).

- **Method**: `POST`
- **Path**: `/api/feedback`
- **Headers**: `Content-Type: application/json`

#### Request Body Specification:
| Field | Type | Required | Constraints | Description |
| :--- | :--- | :--- | :--- | :--- |
| `log_type` | string | Yes | `"qa"` or `"diagnosis"` | Target log table |
| `log_id` | integer | Yes | `>= 1` | Primary key ID returned as `log_id` from Q&A or Diagnosis response |
| `rating` | string | Yes | `"up"` or `"down"` | Feedback rating |
| `comment` | string | No | max 500 chars | Optional user feedback comment |

#### Example Request Payload:
```json
{
  "log_type": "qa",
  "log_id": 42,
  "rating": "up",
  "comment": "Very helpful advice, controlled the pests!"
}
```

#### Success Response (200 OK):
```json
{
  "log_type": "qa",
  "log_id": 42,
  "rating": "up",
  "comment": "Very helpful advice, controlled the pests!",
  "submitted_at": "2026-09-12T10:00:00Z"
}
```

#### Feedback Retrieval Endpoint:
- **Method**: `GET`
- **Path**: `/api/feedback/{log_type}/{log_id}`
- Returns `200 OK` with recorded rating or `404 Not Found` if not rated yet.

#### Idempotent Overwrite Behavior:
Submitting feedback again for the same `(log_type, log_id)` **overwrites** the existing rating, comment, and timestamp rather than rejecting with a duplicate error. This ensures a farmer who accidentally taps thumbs down can immediately tap thumbs up to correct their feedback.

#### Database Architecture Decision: Option A (Direct Columns)
- We adopted **Option A**: adding `feedback_rating` (VARCHAR 10), `feedback_comment` (VARCHAR 500), and `feedback_submitted_at` (DATETIME) directly to `FarmerQALog` and `CropDiagnosisLog`.
- **Why Option A**: Matches existing design conventions (`was_voice_input` and `session_id` stored directly in log tables), requires zero table joins to read an answer and its rating, and avoids table proliferation for a lightweight feedback mechanic. Option B (a separate `Feedback` table) remains an option for future phases if feedback is expanded to non-AI entities.

### 9. Authentication & Authorization (Feature 9)
Provides phone number + password registration and login for both `farmer` and `buyer` roles. Issues signed JWT bearer access tokens (`python-jose`), hashes passwords using `bcrypt`, and protects role-restricted endpoints.

> [!IMPORTANT]
> **Integration Note for Feature 7**:
> Feature 7's listing and offer endpoints currently use loose identifiers (`farmer_id`, `buyer_id`). Feature 9 establishes the foundational authentication and role-checking system. Retrofitting Feature 7 to require real token logins will be completed in Feature 10/11.

#### Endpoints:
1. `POST /api/auth/signup` — Register a new account
2. `POST /api/auth/login` — Authenticate and obtain JWT token
3. `GET /api/auth/me` — Inspect profile of the authenticated token holder

#### Dual-Role Phone Architecture Decision:
- Accounts are uniquely constrained on **`(phone, role)`**, NOT on `phone` alone.
- This allows a user to register both a `farmer` account and a `buyer` account with the same phone number.
- Because of this, `role` (`"farmer"` or `"buyer"`) is required on both `/signup` and `/login` to specify which account is being accessed.

#### Anti-Enumeration Security:
- Failed login attempts due to wrong password or non-existent phone/role return an identical **`401 Unauthorized`** response (`{"detail": "Invalid phone, password, or role"}`).
- This prevents malicious users from enumerating registered phone numbers.

#### Startup Security Enforcement:
- `JWT_SECRET_KEY` has **no working default** in `config.py`.
- The application refuses to boot at startup if `JWT_SECRET_KEY` is missing, shorter than 16 characters, or matches any known insecure placeholder string.

## 🤖 Machine Learning & AI Details

1. **Crop Recommendation**:
   - **Algorithm**: Multi-Class `RandomForestClassifier` (`n_estimators=100`, `random_state=42`)
   - **Dataset**: Atharva Ingle Crop Recommendation Dataset (Kaggle), 2,200 rows
   - **Evaluated Test Accuracy**: **99.55%** on stratified 80/20 train/test split
   - **Input Features (7)**: `N`, `P`, `K`, `temperature`, `humidity`, `ph`, `rainfall`
   - **Output**: Top recommended crop + confidence + 2 alternative crops with confidences

2. **Farmer Q&A Assistant**:
   - **Provider**: Groq Cloud API
   - **Model**: `llama-3.1-8b-instant` (ultra-fast inference, high multilingual competency)
   - **Prompt Engineering**: Strict agricultural domain constraint, direct answer in user's query language, safety disclaimer
   - **Robustness**: 15s explicit timeout, markdown code-block stripping (` ```json `), and regex fallback to prevent 500 errors

3. **Whisper Voice Transcription (Feature 3B)**:
   - **Provider**: Groq Cloud API
   - **Model**: `whisper-large-v3-turbo` (sub-second speech-to-text inference)
   - **Timeout**: Enforced 15-second request timeout
   - **Supported Audio**: `.m4a`, `.mp3`, `.wav`, `.webm` (up to 25 MB)
   - **Multilingual Recognition**: Automatic language detection with optional ISO-639-1 language hint support (Hindi, English, Punjabi, Bengali, Tamil, etc.)

4. **Image-based Crop Diagnosis & Vision Model Decision (Feature 5)**:
   - **Provider**: Groq Cloud API
   - **Configured Vision Model**: `qwen/qwen3.6-27b` (configured as default via `GROQ_VISION_MODEL` in `config.py` and `.env.example`)
   - **Model Tier**: **Preview-tier** (multimodal vision capabilities hosted on Groq)
   - **Contingency Note**: *If this model is deprecated, check the Groq vision documentation at [https://console.groq.com/docs/vision](https://console.groq.com/docs/vision) for its replacement before deploying.*
   - **Failure Resilience**: Groq's multimodal lineup has evolved rapidly and preview models are subject to decommissioning. The backend handles `model_decommissioned`-style errors and timeouts with a graceful HTTP 503 response (`Image diagnosis unavailable, please try again shortly`) rather than crashing or throwing an unhandled 500.
   - **Supported Image Formats & Limits**: `.jpg`, `.jpeg`, `.png`, `.webp` up to 10 MB.
